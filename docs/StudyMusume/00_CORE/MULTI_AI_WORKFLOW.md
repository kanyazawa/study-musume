# Multi AI Workflow

`study-musume` をターミナル中心で複数AIと一緒に進めるときの運用メモ。
目的は `速くすること` ではなく、`混線せずに速くすること`。

## 基本方針

- 1つのAIに1つの主担当を持たせる
- 同じファイルを同時に複数AIへ触らせすぎない
- 最後の統合判断は1つのAIに寄せる
- `PROJECT_STATUS.md` と `TODO.md` を現在地の共通ソースにする

## おすすめ役割分担

### 統合担当

- いま何が終わって何が未完かを把握する
- 仕様と実装のズレを見つける
- docs を更新する
- 最終的な統合確認をする

向いている作業:

- 現在地の整理
- 仕様と TODO の更新
- 複数AIの出力をまとめる
- 最終レビュー

### 実装担当

- 新規機能の実装
- 既存画面の改修
- 部分的なリファクタ

向いている作業:

- Home の UI 実装
- Heroine Select の追加
- 学習モードごとの分岐追加

### 調査担当

- バグ原因の切り分け
- lint / build / test の失敗理由調査
- コードベースの読み取り

向いている作業:

- `undefined` 原因調査
- import 漏れの洗い出し
- 既存状態管理の読み解き

### 発想担当

- UI 案の比較
- 文言改善
- 仕様の穴探し

向いている作業:

- 画面ワイヤー案
- 導線の比較
- キャラ文言の調整

## 一番安全な進め方

### 小さめの作業

同じ workspace で進めてもよい。
ただし、担当ファイルを先に分ける。

例:

- AI A: `Home.jsx`, `Home.css`
- AI B: `docs/StudyMusume/00_CORE/*`
- AI C: 原因分析だけ

### 大きめの並列作業

可能なら AI ごとに別 branch / 別 worktree に分ける。
同じファイルを並列で大きくいじると、最後の統合コストが上がりやすい。

おすすめ:

- `feature/home-heroine-slot`
- `feature/heroine-select`
- `chore/docs-reorg`

## 毎回の流れ

1. `PROJECT_STATUS.md` と `TODO.md` を見て現在地を合わせる
2. 今回の主担当AIを決める
3. 各AIの担当範囲を決める
4. 同じファイルを複数AIに渡さないようにする
5. 実装後、統合担当が build / test / docs 更新を行う

## 標準フロー

この repo では、迷ったらまずこの流れを使う。

1. Claude Code に実装させる
2. Codex に差分レビューだけさせる
3. Codex の指摘を Claude Code に直させる
4. Codex で再チェックする
5. 問題なければ Codex 側で commit する

ポイント:

- 実装担当とレビュー担当を分ける
- 最終 OK と commit の担当は 1つに寄せる
- review の段階では `findings first` で、まず問題を列挙する
- commit 前に必要な build / test を通す
- 区切りがついたら `PROJECT_STATUS.md` と `TODO.md` も更新する

この流れなら、`作るAI` と `止めるAI` が分かれるので暴走しにくい。

## AI に渡すべき最小情報

毎回長文を投げなくても、最低限これがあればかなり安定する。

- 今やりたいこと
- 触ってよいファイル
- 触ってほしくないファイル
- 実装してよいか、原因分析だけか
- 参照してほしい docs

## よくある事故

### 同じファイルを同時に編集する

- 一番起きやすい
- 片方は UI、片方はロジックでも、同じ JSX に触ると衝突しやすい

### 役割を決めずに全員に同じ依頼を出す

- 比較材料は増えるが、統合作業が重くなる
- `案出し` なのか `実装` なのかを分ける

### docs を更新しない

- 途中では問題ないが、数日空くと急に困る
- 区切りのよい完了だけでよいので、自動更新を維持する

### レビュー担当と commit 担当が分かれていない

- 指摘した本人がそのまま直し始めると、役割が混ざりやすい
- 最後に誰の判断で merge / commit したのかも曖昧になる
- `最終チェックと commit は統合担当` と先に決める

## この repo でのおすすめ構成

- 統合担当: Codex
- 実装担当: Claude Code など
- 調査担当: 別AI or Codex の debug モード
- 発想担当: UI 生成系 / 壁打ち系 AI

重要なのは `どのAIを使うか` より `誰が最終統合するか` を決めること。

## 完了時にやること

- build または必要な test を回す
- `PROJECT_STATUS.md` を現在地に合わせる
- `TODO.md` を完了 / 次作業に合わせて更新する
- どのAIが何をやったかを軽く言語化する
- commit する担当を 1つに固定する
